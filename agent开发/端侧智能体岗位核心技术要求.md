# 端侧智能体岗位核心技术要求

## 适用范围与依据

依据用户提供的岗位截图和前序讨论，面向 Android 端侧/系统级智能体架构与应用开发。以下优先级是学习建议，不代表所有雇主统一要求；未将截图中的要求视为个人已具备能力。

- P0：直接决定能否实现可靠的核心链路。
- P1：支撑端侧落地和专家级架构深度。
- P2：按业务和岗位边界专项深入。

## 核心能力矩阵

| 技术域 | 优先级 | 核心知识 | 掌握深度与验证方式 |
| --- | --- | --- | --- |
| Android 系统集成 | P0 | Binder/AIDL、IPC、服务绑定与死亡通知、进程与生命周期、线程模型、权限、后台限制、SystemUI 集成边界 | 能设计跨进程 AI 服务，处理服务断连、客户端死亡、取消和资源回收；区分普通 App、系统 App 与 Framework 的能力边界 |
| Kotlin 与应用架构 | P0 | Kotlin、协程、结构化并发、Flow、MVVM/MVI、模块化、状态持久化、流式 UI | 能让 UI 状态与任务状态一致，处理旋转、离开页面、取消和进程重建；不把长任务仅绑定到页面生命周期 |
| LLM 应用基础 | P0 | Token、上下文、采样、结构化输出、流式协议、模型能力差异、错误与限流 | 能实现统一模型接口，处理不完整流、非法输出、超时、重试和凭据保护；理解生成结果存在不确定性 |
| 工具调用 | P0 | Function Calling、JSON Schema、工具注册、参数校验、授权、幂等、结果结构 | 实现模型提出调用、宿主校验并执行、结果回传的闭环；不会直接执行任意模型字符串；能处理工具失败与重复调用 |
| Agent 执行与会话 | P0 | 固定工作流与自主循环、状态机、执行预算、停止条件、会话历史、检查点、恢复、人机确认 | 实现可追踪、可取消、可恢复的多步任务；明确“结果未知”和“确定失败”在重试上的区别 |
| 评测与可观测性 | P0 | 任务集、工具参数正确率、端到端成功率、执行轨迹、回归、成本和延迟 | 用真实和边界案例比较版本；区分模型、检索、工具、状态和环境问题，展示改进前后数据 |
| 安全与隐私 | P0 | 不可信输入、提示注入、最小权限、数据访问控制、敏感操作确认、日志脱敏 | 将授权检查放在执行层；模型不能自行授予权限；端云回退前检查数据是否允许上传 |
| 端侧模型与推理调度 | P1 | 运行时集成、模型格式与量化概念、CPU/GPU/NPU 支持边界、加载预热、KV Cache、内存预算、请求队列 | 在目标设备完成一次真实推理与资源测量；能解释模型大小、上下文、并发与内存/延迟之间的取舍；不假定运行时自动支持所有硬件 |
| 端云协同 | P1 | 能力探测、模型路由、隐私策略、网络状态、故障回退、版本兼容、模型交付与回滚 | 依据任务、设备、网络、数据敏感性选择执行位置；处理断网与云超时，防止重试造成重复副作用 |
| 上下文与 RAG | P1 | 切块、关键词/向量/混合检索、重排、元数据、引用、访问过滤、历史压缩、记忆边界 | 能定位检索失败和生成失败；历史及外部内容按不可信数据处理；区分会话历史、任务状态、用户偏好和知识库 |
| 多模态交互 | P1 | ASR、TTS、流式音频、打断、音频焦点、图片预处理、多模态上下文、权限与生命周期 | 实现语音输入—任务执行—语音反馈；用户打断时同步取消播放与后续执行，按需求处理回声与环境噪声 |
| 性能与稳定性 | P1 | Perfetto、内存与 ANR 分析、线程/队列、首 Token 延迟、生成吞吐、端到端 P95、功耗、温升 | 明确测量设备、输入、模型、冷热启动与持续负载；优化后验证任务质量是否下降，不只报告 tokens/s |
| GUI 与跨应用操作 | P2 | Intent、公开 API、语义树/截图理解、动作定位、结果验证、系统权限和无障碍边界 | 优先稳定的结构化接口；界面操作需验证动作效果，考虑页面变化和不可逆操作；不假设普通 App 可无限制控制其他应用 |
| 推理底层优化 | P2 | C++/NDK/JNI、交叉编译、算子、量化、硬件后端与内存优化 | 仅在 JD 要求推理框架/内核研发时深入；区分运行时集成、资源调度与内核开发 |
| 框架与协议 | P2 | MCP、一种 Agent 编排框架、工具协议与适配 | 理解协议边界、认证与错误传播；MCP 不等同于 Agent，也不是全部工具调用的必选前置条件 |

## 专家岗位的横向要求

- 将业务目标转成可量化验收标准，确定哪些场景需要 Agent。
- 能说明架构备选方案及取舍，划清客户端、系统服务、模型服务、工具执行和数据层职责。
- 推动跨团队接口、版本演进、发布回滚与线上故障闭环。
- 用实验判断模型、提示词、检索、工具和调度的优化收益。
- 结合具体技术问题跟踪论文与行业进展；专利和创新以有效方案与实际贡献为基础。

## 推荐掌握顺序

1. Kotlin/协程与模型 API：完成文本流式会话。
2. 工具调用与执行状态机：完成一个可取消的多步任务。
3. Android 服务集成：加入 IPC、授权、异常与进程恢复。
4. 评测与追踪：从早期建立任务集，持续做回归。
5. 本地推理与端云路由：在真实设备测量并形成取舍报告。
6. 上下文/RAG 与语音：根据核心场景逐步接入。
7. 按目标 JD 深入 GUI Agent、推理内核或多 Agent。

安全、权限、日志脱敏和指标埋点贯穿整个过程。

## 项目验收清单

- [ ] 文本输入、流式输出和多步工具执行正常。
- [ ] 用户取消后无额外副作用，资源释放可验证。
- [ ] 无权限、非法参数、工具失败均有确定处理路径。
- [ ] 超时后能区分未执行、已执行和结果未知。
- [ ] 进程重建后恢复状态，不盲目重放有副作用的工具。
- [ ] 离线、网络切换、本地模型不可用时按策略处理。
- [ ] 至少一种本地模型与云模型通过统一接口接入。
- [ ] 有任务成功率、错误操作率、延迟、内存和持续负载测试结果。
- [ ] 有架构说明、失败案例和一次可复现的优化对照。

## 针对个人背景的准备建议

用户背景为 Android 系统框架开发，现有系统经验的具体深度仍需通过项目盘点确认。优先补工具调用、Agent 状态管理、评测和模型接入；并核实 Kotlin、协程及大型 App 架构是否存在短板。Python 用于实验、评测和配套服务。初期不以从零训练模型、堆叠框架或多 Agent 作为主线。

## 手机厂核心技术栈映射

以下为基于已提供 JD 的技术选型示例，非所有手机厂共同采用的固定清单。国内 ROM、芯片、模型及自研接口存在差异；不假定具备 Google 服务或 AICore。

| 层次 | 技术栈示例 | 核心产出 |
| --- | --- | --- |
| 交互入口 | Kotlin/Java、Compose 或 View、SystemUI/Launcher 集成、协程/Flow、ASR/TTS | 文本/语音/屏幕上下文入口、打断与执行反馈 |
| Agent 运行层 | 模型 SDK/HTTP 流、JSON Schema、Function Calling、任务状态机、检查点、SQLite/Room | 规划与执行闭环、会话和任务恢复、执行预算 |
| 能力执行层 | AIDL/Binder、Intent、ContentProvider、厂商能力接口、工具注册与鉴权 | 系统与应用能力的可控调用、结果验证与审计 |
| 上下文与记忆 | 文本解析、Embedding、关键词/向量检索、重排、本地结构化存储 | 可追溯且受访问控制的个人知识与上下文 |
| 推理与端云协同 | C++/JNI/NDK（按职责）、一种本地运行时、云模型 API、路由/回退、模型包管理 | 设备适配、资源预算、离线能力、版本兼容 |
| 性能与质量 | Perfetto、Android 内存/ANR 工具、端到端 Trace、Python 评测脚本、回归任务集 | 成功率、错误操作、延迟、内存、功耗与温升的可复现报告 |

本地运行时学习选项可以包括 LiteRT-LM、llama.cpp、MNN 等，选择一种适合目标设备的路线实践即可；支持的模型、量化格式、硬件后端与版本需分别核验。芯片 SDK 和推理内核属于专项岗位深度。Google 的 AICore/Gemini Nano 是系统统一管理端侧模型的一种参考架构，而不是所有手机厂的必选实现。

推荐个人组合：Kotlin/Java + 协程/Flow + AIDL/Binder + Room + 原生模型 API/结构化工具调用 + 自建任务状态机 + 一种本地推理运行时 + Python 评测 + Perfetto。MCP 与编排框架按接入需要学习，不要求把 Python 框架直接嵌入 Android。

厂商差异化重点：屏幕/应用上下文获取、结构化应用能力生态、系统权限与用户授权、模型资源全局调度、跨应用任务结果验证、后台与功耗治理。主动服务另需事件触发、用户偏好、打扰控制与隐私边界。

参考：[Android Gemini Nano/AICore](https://developer.android.com/ai/gemini-nano)。此补充为学习建议，不代表用户已确认调整技术选型。
