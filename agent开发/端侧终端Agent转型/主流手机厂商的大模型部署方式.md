# 主流手机厂商的大模型部署方式

## 问题与结论

用户关心主流厂商如何在手机本地部署大模型，以理解端侧 Agent 的工程方向。以下依据截至 2026-11-01 查阅的公开官方资料，不代表获得厂商内部实现。

从已公开产品架构归纳，常见路线为：经过端侧适配的模型 + 操作系统级 AI 能力管理 + 本地/云端按任务协作。不能将所有厂商、型号、地区和功能视为同一实现，也没有依据认定所有厂商采用同一个运行时。

需要区分三个维度：

1. 计算位置：纯端侧、纯云端或端云协同。
2. 能力承载：系统共享模型服务，或 App 自带模型与运行时。
3. 底层执行：推理引擎通过硬件后端调用 CPU/GPU/NPU；这与模型是否上云是不同问题。

## 已公开的厂商实例

| 厂商/生态 | 官方可确认内容 | 不能据此推出的结论 |
| --- | --- | --- |
| Apple | Apple Intelligence 在本地处理许多任务，更复杂请求可使用 Private Cloud Compute 中的更大模型 | 不能认为所有 Siri/AI 请求均离线，或 PCC 是手机本地计算 |
| Google Android | AICore 是管理端侧基础模型的系统服务；ML Kit GenAI 通过它使用 Gemini Nano，不同应用可共享基础模型 | 不代表所有 Android 手机都有 AICore；系统助手也不等于全部运行在 Nano 上 |

| OPPO | 官方架构包含端侧计算及 Private Computing Cloud 云端扩展 | 不能将私有计算云理解为本地推理，或据此认定具体量化精度/运行时 |

## 本地部署在工程上通常包含什么

以下是工程归纳，不是每个品牌内部实现的已确认清单：

1. 在离线训练环境中完成模型训练和端侧适配，按需要采用蒸馏、量化、稀疏化等方法；手机主要承担推理，个性化记忆不必通过更新权重实现。
2. 将适配模型、Tokenizer、配置等作为受管理资产预置或下载，建立版本校验、设备兼容与更新机制。具体分发方式按平台确认。
3. 由系统 AI 服务或应用运行时加载模型，管理会话、KV Cache、内存、并发、取消、资源释放及温控策略。
4. 推理引擎将支持的算子交给 CPU/GPU/NPU 后端；算子覆盖、量化格式与内存传输决定收益，不能假定全模型或所有环节都由 NPU 执行。
5. 根据模型能力、网络、数据策略、延迟与资源预算选择本地执行、云端执行或拒绝/降级；上云是执行位置改变，不一定是将同一个模型逐层拆到端云运行。

例如 3B 参数全部按 4 bit 存储，纯权重理论约为 1.5 GB（十进制）。实际还需量化元数据、KV Cache、激活、工作区和运行时，因此不能把模型文件大小直接当成总内存需求。此处仅为计算示例，不代表当前手机统一采用 3B/4 bit。

## 与 App 自带模型的区别

- 系统共享服务：App 调 SDK/IPC，由平台统一提供模型能力。Google AICore 是有明确官方文档的实例，可避免多个应用分别下载同一个基础模型；调用受设备、版本和 API 规则约束。
- App 自带运行时：开发者选择模型，使用 LiteRT-LM、llama.cpp、MNN 等适合目标设备的方案，自行承担资产下载、兼容、加载、内存与生命周期管理。这是独立应用和学习验证的可选路线，不能直接当作手机厂商量产实现。
- 工程上不宜假定手机厂商将桌面 Ollama 环境原样搬入 ROM，也不能仅凭用了某品牌芯片就确定推理引擎。

## 对职业转型的意义（建议）

对 Android Framework 背景，优先学习“模型服务的客户端和系统集成”：Binder/AIDL、模型会话与资源调度、端云路由、权限、取消恢复、工具执行与评测。再根据 JD 决定是否深入推理运行时和 NPU 优化。

建议实践：先在 App 内真机跑通一种运行时，再把推理封装为独立服务，通过 AIDL 调用，加入请求队列、取消、服务死亡处理、模型版本与性能观测。这个项目模拟系统集成问题，不意味着已经复刻厂商架构。用户尚未确认执行。
