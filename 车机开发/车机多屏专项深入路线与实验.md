# 车机多屏专项深入路线与实验

## 背景与范围

- 用户已确认：优先多屏专项，要求展开深入学习方法。
- 已有笔记背景：Android Framework，熟悉 PMS、Input，正在学习 WMS；不等于已掌握 WMS 全链路。
- 建议主线：单 Android 实例下的多显示系统 → 同用户跨屏任务 → 输入与 IME → AAOS 乘员区域与并发多用户 → 异常恢复与系统修复。
- 建议基线：无目标项目时可选 Android 15 AAOS 的固定 tag，学习并发可见多用户；实际以可构建、可运行的镜像和目标 JD 为准。不要用 main 文档推断 Android 12/14 厂商分支具有相同功能。
- 多 SoC、多 VM、QNX/Android 混合座舱作为后续架构主题；当前项目范围是一套 Android 管理多个显示屏。
- 返回 [[车机开发/索引]]；前置 [[手机Android系统工程师转车机开发路线与教程]]。

## 如何判断学深了

以“副驾屏启动视频，同时主驾继续导航”为主场景，能回答并提供证据：

1. 目标屏对应哪个 display？此编号如何映射到实际位置？
2. 应用在哪个 user 下运行？Task 最终归属哪个 display？
3. 点击副驾屏时输入事件由哪个设备进入、发给哪个窗口？
4. 谁处于 resumed、visible、focused，为什么它们并不等价？
5. 副驾输入框使用什么 IME 策略？主驾焦点是否受到影响？
6. 用户停止、进程死亡、显示移除或休眠恢复后怎样恢复？

最终产物建议是：实验工程、三条源码链路、五份排障案例、一项可回归的系统行为修改。不是只记住 setLaunchDisplayId。

## 一、先建立六个互相独立的概念

| 概念 | 负责的问题 | 常见误解 |
| --- | --- | --- |
| 物理显示设备 | 画面最终输出到哪块硬件 | 多个物理屏一定对应多个独立桌面 |
| Logical Display / displayId | Framework 如何标识与配置显示 | 把运行时 displayId 当永久座位编号 |
| DisplayContent / TaskDisplayArea | WMS/ATMS 在哪管理窗口与任务 | 创建 Display 就自动具有完整 Launcher |
| Task / Activity / Window / Layer | 运行、窗口与合成处于哪一步 | Task 已在副屏就等于副屏已呈现首帧 |
| User | 应用数据、进程身份与用户生命周期 | 一块屏天然等于一个 user |
| Occupant Zone | 乘员位置与显示、用户等资源的关联 | occupantZoneId、userId、displayId 可以互换 |

概念关系示例：副驾区域 Z 关联用户 U 与显示 D；U 的应用任务放入 D 对应的任务容器。实际映射、访问权限及可用性由系统配置与生命周期决定。

区分：镜像是复用画面；跨屏启动是在目标屏创建/复用任务与 Activity；跨屏移动是改变已有任务归属；Presentation 是在另一显示上展示内容的一种 API。四者的窗口、生命周期和输入语义不同。

## 二、五个递进阶段

### 阶段 1：显示发现与窗口容器（建议 1 周）

阅读入口：DisplayManagerService、LogicalDisplayMapper、DisplayDevice、RootWindowContainer、DisplayContent、TaskDisplayArea。类的位置与实现依分支核对，先回答职责，再看实现。

主链路：显示设备变化 → 显示管理更新逻辑显示与配置 → 窗口管理创建/更新对应 DisplayContent → 显示配置传递到任务与应用。流程涉及回调和异步处理，不应画成单次同步调用。

实验：
- 在开发者选项创建系统模拟副屏，或使用支持多屏的模拟器/开发镜像。
- 用 DisplayManager 枚举 displayId、name、uniqueId、flags、状态与尺寸；输出增删改回调。
- 对照 dumpsys display 与 dumpsys window，确认 Framework 显示与窗口容器的对应关系。
- 连续创建/移除副屏，记录编号与配置变化。模拟屏不等价于带独立触摸的物理屏。

验收：能解释“系统已经发现副屏，但副屏没有桌面”的可能原因，知道继续查 Home、系统装饰与显示策略。

### 阶段 2：跨屏启动与任务复用（建议 1～2 周）

源码入口：ActivityOptions.setLaunchDisplayId、ActivityStarter、LaunchParamsController（含分支对应的 TaskLaunchParamsModifier）、RootWindowContainer、Task、TaskDisplayArea。

阅读问题顺序：谁请求目标屏 → 调用者能否在此屏启动 → 是否复用已有 Activity/Task → 最终落在哪个容器 → 是否发生配置变化 → 窗口是否真的绘制。

实验工程建立 A/B 两个 Activity，显示自身 displayId、user 身份、实例标识、生命周期与 Configuration。不要只看画面猜实例是否复用。

实验矩阵：
- 主屏启动 A，然后指定副屏启动 A。
- 比较 standard、singleTask，以及 NEW_TASK、MULTIPLE_TASK 等相关 flags；一次只改一个变量，记录实际行为，不把某一组 flags 当通用解决方案。
- 从副屏 A 再启动 B，比较显式指定与不指定目标屏的结果。
- 在支持的系统接口和权限下移动已有 Task；与新建 Activity 比较。
- 改变副屏尺寸/密度，观察重建、资源选择和状态恢复。
- 移除副屏，观察任务迁移或销毁，结果取决于目标分支的移除策略和配置。

验收：给出 Activity 实例、Task、display 三者的前后对照表，能从源码说明为什么应用回主屏或复用了旧实例。

### 阶段 3：输入、焦点、IME、系统窗口（建议 1～2 周）

这部分优先复用已有 Input 经验。把触摸路由与按键焦点拆开分析，区分每屏焦点、全局选择策略、应用焦点与 IME 目标。

源码入口：InputReader、InputDispatcher、InputManagerService、WMS 焦点更新相关代码、DisplayContent、InputMonitor、InputMethodManagerService；新版本可能引入不同的 IME 管理分工，按分支追踪。

实验：
- 主副屏各放一个按钮和 EditText，交替点击，记录窗口焦点、输入通道、IME 目标和显示位置。
- 核查输入设备与显示的关联；USB 鼠标/键盘和触摸屏不是相同路由机制。
- 比较可信系统模拟显示与普通应用创建的虚拟显示，识别权限/系统窗口限制。
- 检查副屏 Home、导航栏、状态栏、Dialog 与 IME；核对 Display 上下文和窗口 token。
- 对比“不可点击”“焦点错误”“键盘位置错误”，不要合并为同一个问题。

验收：能用 dumpsys input/window/input_method 及必要 trace 说明事件从设备到目标窗口的路径。不要预设系统必然支持多个用户各自同时打开独立键盘，必须核对具体版本、开关和实现。

### 阶段 4：AAOS 乘员区域与并发多用户（建议 2 周）

前置：同用户双屏实验已经可解释。

阅读入口：CarOccupantZoneManager / CarOccupantZoneService、CarUserManager / CarUserService、Framework 的 UserManagerService / UserController / UserVisibilityMediator（按分支存在性核对），以及设备 RRO。

重点是配置与状态联动：实际显示标识/端口如何绑定区域 → user 如何分配到区域/显示 → user 是否运行、解锁、可见 → Launcher 与应用是否在正确用户下运行。

Android 15 官方文档介绍了非当前前台的完整次级用户在分配显示上提供 UI 的能力，并列出 config_multiuserVisibleBackgroundUsers 配置。打开该 overlay 不代表完整系统自动就绪，还需匹配用户、区域、显示、权限及镜像能力。旧版本厂商实现不可按同一套命令和行为照搬。

实验：
- 先创建和启动测试用户，记录 current/running/unlocked/visible 的差别。
- 使用目标 AAOS 分支支持的接口配置乘员区域与显示映射，并让乘员用户在副屏可见。
- 同一测试包在两个 user 下运行，分别保存不同计数或文本，验证数据隔离。
- 对比“同 user 跨屏”和“不同 user 分屏”的进程身份、任务、数据与生命周期。
- 停止乘员用户、重启应用、重启设备，观察映射和状态是否恢复。

验收：画出 zoneId、userId、displayId、Task、输入设备的映射表；解释为什么副屏有 Home 却不能启动某用户应用。

### 阶段 5：异常恢复与一项系统修改（建议 1～2 周）

优先积累五类案例：启动落错屏、触摸路由错误、IME 错屏/缺失、副屏移除后任务异常、用户/休眠恢复后黑屏。

修复建议：在可控系统工程里改一项可复现、边界清晰的策略，例如自有系统 Launcher 对目标屏失效的处理与状态提示。若尚无平台源码修改能力，先完成应用侧复现与诊断，不能把现象绕过写成 Framework 修复。

回归至少覆盖：主副屏正常启动、目标屏消失、应用死亡重启、用户停止/重启。涉及真正电源恢复需有支持的开发设备；删除模拟显示只验证显示生命周期，不能替代硬件休眠测试。

## 三、统一诊断方法

按“显示 → 用户/区域 → 任务 → 窗口 → 输入 → 合成”收集证据。先确认状态，再推导原因。

```powershell
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
adb shell getprop ro.build.fingerprint
adb shell dumpsys display
adb shell dumpsys activity activities
adb shell dumpsys window
adb shell dumpsys input
adb shell dumpsys input_method
adb shell dumpsys user
adb shell dumpsys car_service
adb shell dumpsys SurfaceFlinger
```

服务名称、输出权限与字段以镜像为准；car_service 仅适用于存在该服务的 AAOS 环境。需要动态时序时再抓 Winscope/Perfetto，静态 dump 不能独立证明事件发生顺序。

基础启动实验：先确认设备当前 user 和 display，再用实际值替换以下占位符；尖括号不是可直接执行参数。

```text
adb shell am start --user <userId> --display <displayId> -n <包名>/<Activity>
```

该命令用于定位与实验，不证明普通应用具有同样权限，也不保证绕过任务复用/目标屏访问规则。并发用户启动参数先读设备上的 am help 与 cmd user help，不跨版本抄命令。

排障对照：

| 症状 | 首轮核查 |
| --- | --- |
| 应用回主屏 | 实际目标显示、调用身份、任务复用、启动模式、LaunchParams、显示访问限制 |
| 副屏无 Launcher | 显示可用性/可信性、系统装饰策略、SECONDARY_HOME 匹配与多实例支持 |
| 可见但不能触摸 | 输入设备映射、目标窗口输入信息、touchable region、遮挡与 display 关联 |
| IME 错屏 | 输入焦点、IME target、显示 IME policy、虚拟屏信任限制 |
| Task 正常但画面黑 | 窗口可见/绘制状态、Surface/Layer、裁剪遮挡、显示电源和最终合成 |
| 乘员应用启动失败 | user 生命周期、安装用户范围、用户显示分配、跨用户权限、zone 配置 |

案例模板：版本/commit → 前置配置 → 复现步骤 → 预期/实际 → 关键时间点证据 → 原因与排除项 → 修改 → 回归 → 未验证边界。

## 四、建议的项目交付

项目名：座舱双屏任务与乘员诊断工具。建议分三版，尚未实施。

- V1 普通应用：显示列表、生命周期日志、目标屏启动、实例与 Task 信息、屏幕变化恢复。受 SDK/权限限制的内部信息由 adb 补充，不宣称普通应用可任意操控任务。
- V2 系统集成：在开发镜像集成区域/用户状态、系统 Launcher 与授权启动策略。
- V3 诊断案例：五类问题的复现、证据与至少一项可回归修改；明确模拟环境未覆盖的触摸硬件与电源边界。

每个阶段应保存正常基线与异常对照。完成标准是能解释分支判断并用状态验证，而不是读完固定数量源码或视频。
