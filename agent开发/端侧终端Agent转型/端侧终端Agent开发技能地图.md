# 端侧终端 Agent 开发技能地图

## 背景与范围

- 用户本轮明确需求：了解转型端侧终端 Agent 开发需要的技能，归档到新文件夹。
- 既有笔记记录的背景：Android 系统框架开发工程师。具体 Kotlin、Python、模型应用开发能力仍需盘点。
- 本文默认“终端”指手机、平板、PC、智能设备中的 Agent，主线按 Android 展开，不指命令行 Terminal Agent。如果目标是 PC 或嵌入式 Linux，需要替换平台集成部分。
- 本文是工程能力与学习建议，未进行招聘市场统计，不代表所有公司统一要求；用户尚未确认新的时间安排、设备与技术选型。

## 结论与岗位选择

端侧终端 Agent 的能力链路是：理解用户目标 → 获取被授权的上下文 → 模型判断下一步 → 校验工具参数与权限 → 执行设备能力 → 验证结果 → 保存任务状态并反馈。

“在手机上运行”不等于“模型全部本地运行”。可采用云端推理、端侧推理或端云协同；应明确哪些任务离线可用、哪些数据允许上传。

| 岗位方向 | 工作重点 | 对当前背景的建议 |
| --- | --- | --- |
| 终端 Agent 应用开发 | 对话交互、模型接入、工具调用、会话与任务管理 | 适合作为转型入口，优先补 Agent 核心闭环 |
| 系统级 Agent 与端云架构 | 系统服务、跨应用能力、权限、资源调度、可靠性 | 与 Android Framework 背景衔接较强，建议作为差异化方向 |
| 端侧推理部署与性能优化 | 模型转换、量化、运行时、CPU/GPU/NPU、内存和功耗 | 先掌握部署测量，再按岗位深入 |
| 推理框架与算法研发 | 算子、编译器、内核、训练与模型压缩 | 属于另一个深度方向，只有目标 JD 要求时才作为主线 |

建议定位：能将模型能力接入 Android 系统，并把多步任务做成可控、可恢复、可评测的终端 Agent 工程师。

## 必须掌握的技能

P0 表示最小可靠闭环必须具备；P1 表示端侧落地需要逐步补齐；P2 按目标岗位专项深入。优先级表示学习顺序，不表示 P1 可以长期省略。

| 技能 | 优先级 | 应学内容 | 掌握标准 |
| --- | --- | --- | --- |
| 编程与工程基础 | P0 | Kotlin/Java、协程/Flow、HTTP/SSE、JSON、Git、基础测试；Python 类型、异步与数据处理 | Android 完成流式调用与取消；Python 能写评测脚本，不必先搭复杂后端 |
| LLM 基础 | P0 | Token、上下文、采样、结构化输出、幻觉、Transformer/注意力基本概念、训练与推理区别 | 能解释模型输出不稳定的原因，处理截断、非法 JSON、超时与限流 |
| 工具调用 | P0 | Tool Calling、JSON Schema、工具描述、参数校验、授权、幂等 | 完成“提出调用—宿主校验执行—回传结果”闭环，不执行任意模型字符串 |
| Agent 运行机制 | P0 | 固定工作流与自主循环、状态机、执行预算、停止条件、检查点、恢复 | 多步任务可取消、可追踪；超时后区分未执行、已执行与结果未知，避免盲目重放 |
| Android 平台集成 | P0 | 生命周期、Binder/AIDL、服务与进程死亡、Intent/ContentProvider、后台限制、Room | 能连接工具服务，处理断连与进程重建；区分普通 App、系统 App、Framework 权限边界 |
| 安全与隐私 | P0 | 最小权限、提示注入、可信执行边界、敏感操作确认、日志脱敏 | 网页、文档和屏幕内容不能改变授权；端云回退前判断数据能否上传 |
| 评测与可观测性 | P0 | 任务集、调用轨迹、成功率、错误操作率、延迟与回归 | 能定位模型、工具、状态或环境失败，用对照实验说明改进效果 |
| 本地模型部署 | P1 | 一种运行时、模型格式、量化、Tokenizer/聊天模板、KV Cache、加载释放 | 真机跑通模型，测内存和延迟；分别验证文本质量与工具调用能力 |
| 端云协同 | P1 | 能力探测、路由、断网回退、模型包校验/更新/回滚、资源队列 | 本地能力不足时按隐私策略降级；避免切换模型后重复执行工具 |
| 上下文与记忆 | P1 | 历史压缩、任务状态、用户偏好、检索、Embedding、引用与访问过滤 | 能区分会话、任务和长期记忆；场景需要时再引入 RAG，能解释检索错误 |
| 多模态交互 | P1 | ASR/TTS、流式语音、打断、音频焦点、OCR/屏幕理解 | 用户打断后能停止播报与后续动作；获取上下文遵守权限和生命周期 |
| 性能与稳定性 | P1 | Perfetto、ANR/Crash、首 Token 延迟、P50/P95、吞吐、内存、温升与功耗 | 固定设备、模型、输入和冷热启动条件测量；持续负载下验证质量和降频影响 |
| GUI Agent | P2 | 语义树/截图、动作定位、跨应用流程、执行后验证 | 优先公开 API 和结构化接口，界面变化后能发现失败；无障碍权限不等于无限控制权 |
| 推理底层 | P2 | C++、NDK/JNI、交叉编译、算子、量化误差、硬件后端 | 推理部署岗位可提高优先级；内核岗位需进一步深入数学、编译器和芯片架构 |
| 框架与协议 | P2 | 一种编排框架、MCP 的工具协议与鉴权边界 | 先理解原生执行循环，再按项目引入；MCP、多 Agent 都不是入门前置条件 |

## 适合当前背景的技术组合

建议组合：Kotlin/Java + 协程/Flow + Binder/AIDL + Room + 模型 API/结构化工具调用 + 显式任务状态机 + 一种本地推理运行时 + Python 评测 + Perfetto。

- 已有系统经验可迁移到服务集成、并发、权限、故障定位和资源治理；这不等于已经具备 Agent 开发经验。
- 优先补工具调用、任务恢复、模型能力判断和评测，而不是重复从头学习 Android。
- 运行时只选一种适配目标设备的路线。可考察 LiteRT-LM、llama.cpp、MNN 等，模型格式与硬件支持需要单独核验。
- Google 官方将 LiteRT 定位为端侧推理引擎，并为对话、KV Cache 和工具调用场景指向 LiteRT-LM。具体设备、模型和后端支持仍以所用版本为准。[LiteRT 官方概览](https://developers.google.com/edge/litert/overview)
- ML Kit GenAI 基于 AICore 使用端侧基础模型；不能假定所有 Android 设备、国内 ROM 都具有对应能力。[ML Kit GenAI 官方概览](https://developers.google.com/ml-kit/genai)
- ONNX Runtime 的硬件加速依赖 Execution Provider；算子不支持导致分图时可能损害性能，因此“支持某后端”不代表模型全图都能加速。[官方移动部署说明](https://onnxruntime.ai/docs/tutorials/mobile/)

## 建议的项目与推进顺序

建议主项目：Android 终端任务助手。用户输入“搜索本地示例笔记，将指定内容整理成摘要并保存到应用内待办”，系统通过检索、摘要、保存、查询验证等工具完成闭环。先使用应用自己的数据，后续再接入获得授权的系统或跨应用接口。

1. **文本与模型接口**：流式输出、取消、错误展示；用接口隔离云端和本地实现。
2. **工具闭环**：先做 3—5 个确定性工具，加入参数校验、执行权限和结果验证。
3. **可靠任务**：状态落库、检查点、超时处理、进程恢复和副作用去重。
4. **端侧落地**：真机部署一个模型，比较云端/本地的任务质量、延迟和内存；本地模型能力不足时明确降级。
5. **系统集成**：用 AIDL 连接工具服务，验证服务死亡、后台约束、资源回收；普通 App 权限范围以外的功能使用模拟接口并标注。
6. **评测与展示**：建立包含正常、无权限、非法参数、断网、重复调用、取消、进程死亡、提示注入等案例的任务集，保存版本对照结果。

建议先建立约 30 条任务作为起始回归集，再随真实失败扩充；这是实践建议，不是统计充分性或行业合格标准。不重新指定学习周数，既有 [[Agent学习执行总表与视频导航]] 仍保留原有执行入口地位。

## 求职时应能展示的证据

- 一个可运行、可复现的真机演示和架构图。
- 一条从用户输入到工具结果验证的完整 Trace。
- 取消、断网、进程死亡和结果未知时的处理记录。
- 固定条件下的任务成功率、错误操作率、P95 延迟、峰值内存与持续运行报告。
- 至少一次优化前后的对照，以及为何选择该模型、运行时与执行位置的说明。
