# Android 系统工程师转型 Agent 开发路线

> 来源：2026-10-24 聊天整理。记录已讨论的背景、建议与学习安排；时间规划和项目均为建议，尚未确认开始执行。

## 背景与目标

## 职业定位建议

### 2026-11-14 补充：保留资历与尽快变现

用户再次明确：资深 Android 系统框架背景，希望转型 Agent，同时保留历史积累、尽快变现。尚未确认是以转岗涨薪还是副业收入为首要目标；以下均为建议，未视为已确定执行。

建议定位为“懂 Android 系统的 Agent 工程负责人”，将权限、IPC、状态机、性能、故障诊断经验用于 Agent 的可靠执行与终端集成。岗位级别仍取决于实际项目和交付证据，不保证薪资或转型期限。

区分两种路径：

| 路径 | 推荐切入口 | 收入形成条件 |
| --- | --- | --- |
| 转岗或内部转型 | Android AI、终端助手、Agent 系统集成、端云协同 | 有相应需求、有效岗位和可证明的工程能力 |
| 副业或技术服务 | Android 故障诊断、回归测试与日志分析提效 | 有可接触客户、真实痛点、授权数据和付费试点 |

建议先利用现有行业关系验证需求。通用聊天助手、纯课程学习和从零训练模型不作为当前最快形成收入证据的主线。若已有端侧岗位机会，继续采用下文及 [[端侧智能体岗位匹配与路线调整]] 的 Android 助手作品；若优先副业，先选窄范围的诊断服务，不同时开发两个完整产品。

#### 建议的首个付费试点

Android 系统故障诊断助手，第一版只选本人最熟悉的一类问题，例如 ANR 或 WMS/Display 异常。输入授权且脱敏的日志，输出带来源的时间线、根因候选、证据、缺失信息和下一步操作。确定性解析由程序完成，模型组织分析，并由工程师复核。

完整 Agent 的判断标准是能按线索选择工具、读取新增证据并决定继续调查或停止；单次上传日志生成报告属于有价值的起步工作流，不必包装成自主诊断系统。

先交付诊断提效服务，再视复用需求产品化。收费范围按样本数、支持故障类型、交付周期、部署方式、验收和人工复核责任约定；目前没有客户预算或成交数据，不提供市场报价与收入承诺。避免承诺自动定位全部根因。

#### 六周验证建议

假设每周可投入 10—15 小时且能获得授权案例，时间仅为实验安排：

1. 第 1 周：访谈约 5 位熟悉的研发或测试负责人，确认重复排障场景、当前耗时、预算负责人、数据可用性；整理约 20 个历史案例并预留未参与调试的验收样本。
2. 第 2 周：实现单类问题最小闭环，补 Python、结构化输出、工具调用、日志解析和必要检索。
3. 第 3—4 周：与人工和简单脚本对比，记录工程师完成诊断的时间、结论证据支持程度、错误根因率、模型成本；形成演示、架构图和失败复盘。
4. 第 5—6 周：争取边界明确的付费试点，或携作品开展内部转岗与岗位面试。客户付费意愿弱时，调整场景或把作品用于求职，暂缓扩大开发。

建议把“诊断耗时降低 30%”作为待实测的试点目标，绝非已有成果。准确率口径必须明确，根因未知的样本不能当作已确认标签。

近期必补：模型调用、工具参数校验、上下文与检索、执行状态、超时恢复、评测和成本。MCP 按接入需要学习；多 Agent、模型微调、底层算子优化按明确需求后置。Android 系统级执行需说明普通 App、ADB 授权、系统签名或定制 AOSP 各自边界。

当前官方 ML Kit 文档已有 Gemini Nano/AICore 的 agentic workflows，但涉及开发者预览与设备条件；不能假设国内客户设备均可使用。首个诊断原型可在开发机运行，模型部署位置由客户数据要求决定。

参考：[ML Kit agentic workflows](https://developers.google.com/ml-kit/genai/agent/android)、[接入与设备条件](https://developers.google.com/ml-kit/genai/agent/android/get-started)。本次查阅用于验证技术入口，未据此推断招聘规模或客户需求。

待确认：转岗或副业优先级、可投入时间、可接触的客户/团队、本人最擅长的系统故障类型、授权数据来源。已完成工作仅为路线分析与笔记更新，尚未实施项目或获得付费客户。

以“有 Android 系统工程背景的 Agent 应用工程师”为切入点，优先考虑研发提效、终端智能体和设备诊断场景，逐步积累专家岗位需要的架构与交付能力。

核心补课方向：把具有不确定性的模型接入需要稳定交付的软件系统，包括模型基础、上下文和检索、工具调用、效果评测及 Python 服务开发。

## 学习内容与优先级

### 第一层：Python 和模型调用基础

目标：独立开发并部署一个模型应用服务。

- Python：类型标注、异步编程、异常处理、依赖管理。
- 服务端：FastAPI、HTTP、SSE 流式输出、数据库、Docker。
- 模型基础：Token、上下文窗口、Embedding、采样、幻觉、结构化输出。
- API 实践：多轮会话、超时、重试、限流、成本统计。
- 原理基础：理解 Transformer、注意力及训练与推理的基本区别；初期无需从零训练大模型。

### 第二层：Agent 核心执行机制

需要能独立实现并解释以下链路：

用户目标 → 构造上下文 → 模型选择工具 → 校验参数和权限 → 执行工具 → 返回结果 → 继续执行或结束。

- Tool Calling、JSON Schema、工具描述设计。
- 固定工作流与自主 Agent 的适用边界。
- 状态管理、执行预算、停止条件、失败恢复。
- 人工确认、幂等性与重复执行处理。
- MCP 的用途、客户端与服务端关系、授权边界。

建议先用原生 SDK 实现完整循环，再选择一个编排框架深入。框架需要服务于明确的问题。

### 第三层：RAG 和上下文工程

目标：让模型基于代码、文档和历史案例可靠工作。

- 文档解析、切块、元数据、增量更新。
- 关键词检索、向量检索、混合检索、重排序。
- 代码检索与普通文档检索的区别。
- 引用溯源、信息冲突、无答案时的处理。
- 会话历史压缩、任务状态与长期记忆的边界。

排错时区分：没有检索到、检索错误、模型拿到材料后理解错误。

### 第四层：评测与生产工程

目标：能够量化效果，定位失败，并稳定交付。

- 建立真实任务集，定义成功和失败。
- 记录模型调用、工具执行、检索和最终结果。
- 衡量任务成功率、错误操作率、延迟及单任务成本。
- 对模型、提示词、检索策略、工具设计做对照实验。
- 处理提示注入、越权调用、数据泄漏和工具失败。
- 实现回归验证、灰度发布、回滚。

## 主线项目：Android 系统故障诊断 Agent

### 项目目标

利用 Android 系统经验，做出有技术深度、可演示、可评测的应用。

输入：经过脱敏的 bugreport、logcat、ANR traces、tombstone，以及对应版本的代码和文档。

处理流程：

1. 识别故障类型，提取关键时间线。
2. 调用解析、检索和代码查询工具。
3. 给出根因假设，并逐项关联证据。
4. 区分已确认事实、推测和缺失信息。
5. 输出下一步排查方案。

### 迭代安排

| 阶段 | 交付内容 | 体现的能力 |
| --- | --- | --- |
| V1 | 日志解析工具、结构化诊断报告 | Python、模型调用、工具设计 |
| V2 | 关联 AOSP 文档、源码、历史案例 | RAG、上下文组织、证据溯源 |
| V3 | 多步调查、状态保存、失败恢复 | Agent 编排与可靠性 |
| V4 | 固定评测集、对照实验、部署监控 | 架构判断、效果优化 |

设计原则：日志解析、时间计算和关键字段提取尽量交给确定性代码；模型负责综合分析和提出调查方向，便于定位错误与评测。

后续可扩展终端操作项目：通过 ADB 完成测试和复现任务。修改设备状态的操作需要权限检查和人工确认机制。

## 建议学习节奏

假设每周投入 10—15 小时，按 16 周安排。此安排是学习建议，不意味着完成后即可获得专家岗位。

| 时间 | 重点 | 交付物 |
| --- | --- | --- |
| 第 1—4 周 | Python、模型 API、结构化输出、工具调用 | 日志分析服务 V1 |
| 第 5—8 周 | 检索、Embedding、混合检索、引用 | 可追溯的知识检索与诊断 |
| 第 9—12 周 | 编排、持久化、恢复、MCP | 完整多步诊断 Agent |
| 第 13—16 周 | 评测、成本、延迟、安全、部署 | 可演示系统和实验报告 |

每个阶段保留：代码、设计取舍、效果数据。用于复盘和面试展示。

## 投入取舍

- 编排框架选择一个深入，避免同时铺开多个框架。
- 微调按项目需要再学。
- 单 Agent 出现明确瓶颈后，再考虑多 Agent。
- 机器人开发保留为后续方向，当前先打通 Agent 主线。
- 用系统诊断或终端研发工具建立差异化，再用评测、架构和交付能力支撑专家岗位定位。
