## 教学偏好与使用方法

用户已明确：窗口与容器等概念必须形象、易懂、便于记忆。这是后续 WMS 讲解的持续要求。建议每个概念按“为什么需要 → 生活画面 → Android 实例 → 准确定义 → 容易混淆处 → 自测”展开，不用术语解释术语，不默认讲过就已掌握。

本篇先用商场理解归属和分组，再用舞台理解画面与输入。两个类比各自解释一类问题，避免硬凑一种现实物体对应所有技术对象。类比仅帮助记忆，准确关系以两篇入门课和源码为准。本次未新增源码核验或设备实验。

## 1. 商场：理解容器为何存在

设想系统管理很多商场，每个商场内部有不同经营区域，每个区域组织多个办事场所，场所中又有不同办理环节与服务台。管理方需要知道“它在哪、属于谁、整组怎样移动或调整”。

| Android 概念 | 记忆画面 | 准确含义与现实例子 | 记忆句 |
|---|---|---|---|
| WindowContainer | 通用的分组管理规则：能登记上下级、排序、调整范围 | 服务端容器共同基础，支持父子关系、配置与层级等管理；不是另一间实际商铺 | 容器是管理能力，不必自己有画面 |
| RootWindowContainer | 管理所有商场的总台账根目录 | 组织各 display 的管理根入口 | Root 管所有显示 |
| DisplayContent | 一座商场的管理档案 | 一个 display 在 WMS 中的管理对象；主屏、副屏分别有对应对象 | 一显示，一套管理对象 |
| DisplayArea | 商场的分区规则和管理分组 | 按策略组织窗口/任务，可嵌套；不一定是可见矩形 | Area 分组，不必画框 |
| TaskDisplayArea | 专门安排办事场所的区域 | 一类负责组织 Task 的 DisplayArea | TDA 放任务 |
| Task | 一次完整办事流程的组织夹 | 组织 Activity/子任务，参与导航、窗口模式等管理；例如列表→详情→确认页面可同属一个 Task | Task 管一串页面 |
| root task | 当前区域内处于根任务层级的那个组织夹 | Task 的角色，可组织子 Task，也可承载 Activity；不是另一个专门类 | root 是位置角色 |
| TaskFragment | 办事流程里的子分组，可安排并排的两个办理区 | Activity 等内容的容器，可用于任务内嵌入；Task 自身也继承它的能力 | Fragment 分组，Task 自带此能力 |
| ActivityRecord | 管理处记录某办理环节的档案 | 服务端代表一个 Activity，参与生命周期和窗口管理；不是应用里的 Activity 实例 | Record 在系统，Activity 在应用 |
| WindowToken | 一组相关服务台的归属组织 | 服务端组织相关窗口的一类容器；ActivityRecord 继承它 | Token 容器管归属 |
| WindowState | 某服务台在管理处的动态档案 | 一个实际窗口的服务端核心对象，跟踪属性和状态 | State 记一个窗口 |

“商场管理档案”是帮助区分物理显示和服务端对象，不表示 DisplayContent 只保存静态数据。Task 的“办事流程”也不保证线性或永不重组。

## 2. 运行时包含与类继承：盒子和能力要分开

包含关系：一个盒子实际装了什么。继承关系：这个盒子具有什么种类的能力。

现代代码中 Task 是 TaskFragment 的子类，不要求每个 Task 下还放一个额外 TaskFragment。类似“轿车是一种汽车”，不等于每辆轿车里面都装一辆独立汽车。

ActivityRecord 是 WindowToken 的子类，同理不要求再套一个独立 WindowToken 对象。

普通应用路径示意，省略区域与可选层级：

```text
RootWindowContainer：全局根
└─ DisplayContent：默认显示
   └─ ……DisplayArea……
      └─ TaskDisplayArea：任务区域
         └─ Task：聊天任务
            ├─ ActivityRecord：聊天列表
            │  └─ WindowState：列表主窗口
            └─ ActivityRecord：聊天详情
               ├─ WindowState：详情主窗口
               └─ WindowState：普通 Dialog（示意）
```

记忆主干：“显示→区域→任务→Activity→窗口”。它是概念路径，不是每台设备的固定完整树。IME、状态栏等非 Activity 窗口有自己的 token/区域组织，不强行挂到聊天 Task 下面。Task 也可嵌套子 Task，或有独立 TaskFragment 子节点。

## 3. 舞台：理解窗口、内容与最终画面

接下来只讨论一个界面怎样出现：把屏幕想成舞台，多个窗口像舞台上的不同节目展示单元。以下角色解释职责，不代表实际对象数量一一对应。

| 概念 | 记忆画面 | 准确定义与区别 |
|---|---|---|
| Activity | 某一幕的应用侧负责人 | 应用交互组件，有生命周期，不是窗口图像本身 |
| Window/PhoneWindow | 这一幕顶层界面的承载与外观安排 | 应用侧窗口抽象及常见实现；不同于服务端 WindowState |
| DecorView | 这一幕的最外层布景架 | 常见顶层 View，容纳内容及主题相关结构 |
| View | 布景架上的文字、按钮、输入框 | 窗口内部的控件/布局节点，通常不是独立窗口 |
| ViewRootImpl | 应用布景团队与系统舞台管理之间的联络员 | 协调顶层 View 树的布局、绘制、输入及服务交互；自身不是 View |
| WindowManager | 应用提交布置申请的接口 | add/update/remove 等客户端窗口管理接口 |
| WMS | 舞台场务管理 | 协调窗口位置、大小、层级、显示策略、焦点等；不负责画出每个按钮 |
| ATMS | 节目流程与场次组织 | Activity/Task 启动、生命周期和导航管理，与 WMS 协同 |
| Input | 收到观众操作并按规则投递的系统 | 路由按键、触摸等事件；与窗口提供的输入信息协作 |
| Surface | 向图形链路供画面的生产接口 | 应用通过相关绘制机制提供图像内容，不是一张静态图 |
| buffer | 某次生产出的画面数据 | 不是窗口本身，也不是图层管理对象 |
| SurfaceControl | 控制图层摆放的操作接口 | 设置位置、透明度、裁剪、父子关系等 |
| Transaction | 一组打包提交的布置指令 | 协调一组图层状态变化，不等于绘制全部像素 |
| Layer | 可以组合的画面层或组织节点 | SF 合成层级中的节点，有的承载内容，有的是容器 |
| SurfaceFlinger | 把各路图层内容组织合成的合成台 | 与硬件合成/显示链路协作输出画面 |
| WM Shell | 承担部分转场和多窗口交互的执行团队 | 不是 adb shell 命令行；具体职责随版本产品演进 |

记忆：“应用画内容，WMS 管窗口，SF 合画面”。这句话仅概括主要职责，不表示所有图层状态都只能由 WMS 写入。

## 4. 位置、输入与显示术语：用一句生活问话记住

| 术语 | 记忆问话 | Android 场景 |
|---|---|---|
| bounds/frame | 这组内容/这个窗口占哪块地方？ | Task bounds 与 Window frame 是不同对象的范围，可能采用不同坐标系 |
| Z-order | 谁挡在谁前面？ | Dialog 通常盖在 Activity 内容上；具体还涉及父子和相对层级 |
| type | 你是哪类展示单元？ | 应用窗口、子窗口、系统窗口走不同管理规则 |
| flags | 你允许哪些行为？ | 可否获得焦点、接收触摸、让背景变暗等 |
| Binder token | 这次申请关联哪个所属身份？ | 不同接口 token 含义不同，不能统一叫万能权限票 |
| focus | 键盘或遥控器的操作对象是谁？ | 按键焦点不等于任意坐标的触摸目标 |
| touchable region | 点在哪些位置算点到你？ | 命中区域不必等于肉眼看到的全部区域 |
| alpha | 这层有多透明？ | 本层或祖先透明都可影响结果 |
| crop | 允许露出的画面范围多大？ | 画面存在但被裁掉仍然不可见 |
| transform | 整体移动、缩放、旋转成什么样？ | 转场或旋转可通过父层变换影响内容 |
| Insets | 哪些区域受系统栏、IME等影响，需要处理重叠？ | 应用可绘制到这些区域，再根据 Insets 适配内容 |
| IME | 谁提供文字输入界面？ | 输入法请求、目标、窗口、Insets、动画要配合 |
| relayout | 窗口安排是否要重新协商/更新？ | 不只等于某个 View.layout 执行 |
| Transition | 从一幕到另一幕怎样协调变化？ | 打开应用、返回、进入分屏，不只是视觉动画 |
| leash | 把多块布景挂到同一控制架再一起动 | 动画用临时父节点统一变换，结束时需恢复/清理 |

## 5. 五个“不是一回事”，对应五种问题

1. 登记了节目 ≠ 已经有画面：WindowState 存在，不代表首 buffer 就绪。
2. 有画面 ≠ 看得到：可能透明、裁剪、遮挡或位置不对。
3. 看得到 ≠ 有焦点：多个窗口可以同时可见，焦点有自己的选择规则。
4. 有焦点 ≠ 所有触摸都归它：触摸还按区域、窗口规则、display 等路由。
5. 一个窗口 ≠ 一个 Layer：内容、子 Surface、容器、动画 leash 可形成多节点。

## 6. 三棵树的记忆

- View 树：**内部装修图**，按钮、输入框怎么布局。
- WMS 容器树：**归属组织图**，哪个显示、区域、任务、Activity 管着哪个窗口。
- SF Layer 树：**画面组合图**，哪些图层挂在一起、如何变换与合成。

同一个问题可能跨三图，但不能把三图当成同一结构。

## 7. 复习方法与自测

建议第一次先记主干与区别，第二次脱稿画树，第三次用“聊天→Dialog→输入法→分屏”串故事。隔天、三天后、一周后各复述一次；这是学习建议，未设置提醒，也不表示用户已采用。

- 聊天页增加一个按钮，首先变哪棵树？答：通常是 App View 树。
- 弹普通 Dialog，为什么通常不新建 Task？答：窗口增加不等于任务或 Activity 增加。
- 把整个聊天任务移到另一显示，先想哪个对象？答：任务组织/归属及相应配置、图层和输入更新，而不是逐个搬 Button。
- 为什么 ActivityRecord 下面不必再画 WindowToken？答：它本身继承 WindowToken。
- 为什么没有独立 TaskFragment 节点仍不奇怪？答：Task 自身继承 TaskFragment，额外节点按场景存在。
- 看到黑屏先问什么？答：窗口是否存在、内容是否就绪、图层是否可见、是否被遮挡、呈现是否及时，逐层验证。
